## 发现的 Bug / 体验问题

### Bug #1（中等）：学生加入班级接口对邮箱做了比其他接口更严格的"可投递性"校验，与测试计划指定的 `@example.test` 域名不兼容
- 位置：`schemas.py` 第 120-123 行 `StudentJoinRequest.email: EmailStr`。
- 现象：使用 `student.a.e2e.*@example.test` 通过加入链接注册时返回 `HTTP 422: email: value is not a valid email address: The part after the @-sign is a special-use or reserved name that cannot be used with email.`
- 根因：`StudentJoinRequest`/`StudentJoinResponse` 使用 pydantic 的 `EmailStr`（底层 `email_validator`），默认开启了"可投递性"检查（会对域名做真实 DNS MX 查询）。`example.test`、`example.com`、`example.org`、`example.net` 等 RFC 2606 保留测试域名均无 MX 记录或被显式列入 special-use 保留名单，因而被拒绝。
- 不一致之处：同项目中 `TeacherEntryRequest.email`、`StudentLoginRequest.email`、`StudentCreate.email`（教师手动添加学生用）都只是 `str` 类型，不做此校验——这正是教师注册、学生 B（手动添加）用 `@example.test` 都能正常工作，唯独"学生自助加入班级"这一条路径失败的原因。
- 影响：真实场景下如果学校/机构的邮箱域名在某些网络环境下 DNS 查询超时或该域名确实没有配置 MX 记录（内部邮箱系统常见），学生会被无法自助加入班级，且报错信息是英文、技术性很强，普通学生难以理解。
- 临时规避：本次测试改用公共测试邮箱域名 `mailinator.com`（有真实 MX 记录，应用本身从不真正发信，不存在隐私泄露风险）完成了学生 A 的加入流程。
- 建议：如果本来就不需要真正给学生发邮件验证，`StudentJoinRequest`/`StudentJoinResponse` 的 `email` 字段改为普通 `str`（或 `EmailStr` 但关闭 `check_deliverability`），与项目里其他邮箱字段的校验强度保持一致。

### Bug #2（中等偏高，影响自动化测试与潜在的可用性/安全问题）：学生管理页"重置密码"使用原生 `window.prompt()` 弹窗
- 位置：`frontend/src/teacher/pages/TeacherStudentsPage.tsx` 第 41 行 `window.prompt("请输入该学生的新密码：")`。
- 现象：点击"重置密码"按钮会触发浏览器原生 `prompt()` 对话框。该对话框会阻塞渲染进程，导致 Chrome 扩展（claude-in-chrome）完全无响应（`Input.dispatchMouseEvent` 超时、`javascript_tool`/`get_page_text` 均超时），且该对话框无法通过页面脚本注入（覆盖 `window.confirm`/`window.alert` 对 `window.prompt` 无效）关闭，最终只能关闭整个标签页才能恢复。
- 影响：
  1. 完全无法通过浏览器自动化/E2E 测试框架测试这一功能（本报告中该步骤因此改为直接调用后端 API 验证逻辑正确性，UI 路径未能验证）。
  2. 产品体验角度：原生 `prompt()` 样式无法定制、在部分浏览器/系统里可能被输入法/密码管理器干扰，且没有"确认密码"二次输入框，容易误输入。
  3. 新密码通过 `prompt()` 明文显示在弹窗里（虽然这是浏览器原生行为，所有 prompt 都明文，但对"密码"这种敏感输入用 `prompt()` 而非表单内的 `type="password"` 输入框，体验和安全观感都不佳）。
- 已做的变通验证：直接调用 `POST /courses/{course_id}/students/{student_id}/password`（教师 JWT 鉴权）确认：重置成功返回 `{"detail":"密码已重置。"}`；重置后用旧密码登录返回 `401 邮箱或密码错误。`；用新密码登录返回 `200` 并正常签发 token。**后端逻辑本身正确**，问题仅在前端交互方式。
- 建议：把"重置密码"改成页面内的表单（输入框 + 确认按钮），而不是 `window.prompt()`，同时能提供最小长度等客户端提示，并与其余操作保持一致的确认体验。

### 观察（非 bug，仅记录）：作业的"满分"字段与批改总分口径不一致
- 创建作业时"满分（可选）"留空，系统按 100 显示（`assignments.max_score = 100.0`）。
- 但实际批改结果的 `max_total_score` 是按官方答案文档里解析出的题目分值累加得出的（本次为 19 分：18 道小题各 1 分 + 1 道合并大题 1 分），与作业配置的"满分 100"没有任何关联或换算。
- 这不影响功能正确性（前端各处显示的"总分"都是以 `max_total_score` 为分母，口径自洽），但对老师而言，"创建作业时填的满分"字段目前形同虚设，容易造成困惑（例如老师可能以为满分是 100，但列表里显示的是"19/19"）。建议要么在作业管理页说明这个"满分"仅用于展示占位、不参与实际批改计分，要么让批改总分按该满分做归一化换算。
